# Reuse the cached MRO for subclass queries (2026-09-30)

Removing temporary inheritance-vector allocations improves the official
pure-Python unpickle benchmark by **1.10×** over the unchanged XLang3 parent.
This is a generic runtime optimization. CPython's pure-Python library code,
including `pickle.py`, remains Python.

## Change and semantic guard

Every ordinary instance truth test checks whether the class inherits from
the builtin numeric classes before resolving `__bool__` or `__len__`.
`class_is_subclass()` previously copied the class's cached Value MRO into a
fresh `std::vector<const ClassObject*>` for each query. The copying and vector
growth caused heap allocations even though the cached inheritance order had
not changed.

The final query reads that same Value MRO directly and compares the validated
class pointers without repeating Value-tag/object-kind checks. The existing class-version
guard still rebuilds it after class or base mutations. No numeric conversion,
special-method lookup, descriptor binding, truth return validation, or
exception behavior is bypassed. The code comment beside
[`class_is_subclass()`](../../src/runtime/object_model.cpp) records the hot-path
reason and invalidation requirement.

The helper is explicitly outlined with `XLANG3_NOINLINE`. The initial
allocation-free version passed the complete release gate but showed small
repeatable slowdowns in unrelated local-slot and function-call workloads.
Pointer-only membership and then a preserved call boundary removed those
slowdowns in the focused comparison. These changes can affect native code
layout and inlining; measurements do not isolate every compiler mechanism.
The final version requires its own complete gates, not just the focused cases.

The new [semantic fixture](../../tests/fixtures/core/subclass_cached_mro.py)
warms subclass queries, changes a class's bases, checks descendant invalidation,
restores the hierarchy, and exercises multiple inheritance and numeric
subclass truth. It also changes an instance's inherited `__len__` through base
replacement and later method mutation. Its expected output is generated by
CPython 3.14; the entire XLang3 fixture runner passed with exit 0 after the
change: 301 core fixtures, 11 compatibility sections, and three expected
failures.

The [native profile](native-vm-opcode-profile-20260930.md) motivated this
investigation by attributing about 8% of instrumented positive self-time to
`JumpIfFalse`. Its shares are diagnostic only. The following official scores
come from ordinary, uninstrumented Release executables.

## Official benchmark comparison

Both XLang3 sides ran the unchanged pyperformance 1.14.0
`bm_pickle/run_benchmark.py`, pyperf 2.10.0, and
`--rigorous --pure-python --protocol 5 unpickle`. Each contains 120 measured
values. The common compatibility shim disabled unsupported Windows process
priority and host metadata hooks; calibration, subprocess sampling, and the
timed Python workload stayed intact. The two runtimes used separate cache
directories.

| Runtime | Mean ± standard deviation | Speed with CPython = 1.0× |
|---|---:|---:|
| CPython 3.14.7, fresh rigorous reference | 0.1638 ± 0.0030 ms | 1.000× |
| XLang3 unchanged parent, final reverse-order pair | 4.3665 ± 0.0656 ms | 0.038× |
| XLang3 outlined candidate | 3.9671 ± 0.0727 ms | 0.041× |

Speed is CPython time divided by XLang3 time. The candidate takes **24.22×
longer** than this CPython reference, compared with **26.66×** for the parent.
This improvement does not meet the goal of beating CPython. The CPython
reference was rerun after the final candidate and parent measurements.

The final rigorous XLang3 comparison is **1.10× faster**, significant at **t = 44.68**,
with a **9.15% time reduction**. A preceding reverse-order fast pair of the initial variant also
favored the candidate: 4.26 ± 0.03 ms to 3.96 ± 0.05 ms, **1.08× faster**,
significant at t = 24.36. Fast samples are supporting evidence; the rigorous
pair is the reported result.

## Release validation

The final complete default 11-case fixed-baseline and immediate-parent gates
both passed with exit 0. Each used 21 order-balanced sample pairs, five
warmups, every default case, and the unchanged 10% per-case tolerance. The
fixed accepted baseline was preserved; it was not replaced by this candidate.
The outlined change is retained.

Ratios below are candidate elapsed time divided by the immediately preserved
parent time. Values below 1.0 are faster. These local workload ratios are not
CPython speed comparisons.

| Case | Elapsed ratio | Paired 95% interval |
|---|---:|---:|
| `local_slots` | 1.037× | 1.031–1.043× |
| `scalar_arithmetic` | 0.996× | 0.992–1.003× |
| `range_for` | 1.001× | 0.988–1.025× |
| `function_calls` | 0.989× | 0.976–0.995× |
| `class_construct` | 1.006× | 0.997–1.011× |
| `list_append` | 1.008× | 0.974–1.051× |
| `property_access` | 0.994× | 0.982–1.004× |
| `deepcopy_memo` | 0.985× | 0.979–0.999× |
| `json_dumps` | 0.983× | 0.981–0.984× |
| `gc_traversal` | 0.926× | 0.916–0.943× |
| `subparsers` | 0.991× | 0.986–0.997× |

The complete parent run measured `local_slots` 3.75% slower. The earlier
focused comparison of the identical binary measured it 3.03% faster, with an
opposite interval. The per-run paired intervals do not capture all variation
between runs, so neither result establishes a uniform local-slot improvement.
The smaller cases are mixed. The official unpickle gain is supported across
both rigorous variants, and the final full gate also favors function calls,
deepcopy, JSON, GC traversal, and subparsers. All raw results are preserved;
the slower local-slot result has not been discarded or hidden.

## Variant evidence

The initial Value-checking variant measured 4.3246 ± 0.0848 ms for its parent
and 3.9492 ± 0.0712 ms for its candidate: **1.10× faster**, t = 37.16. It passed
both complete gates but had 4.26% slower `local_slots` and 3.05% slower
`function_calls`, with paired intervals excluding 1.0. This version was
superseded instead of treating the release tolerance as a slowdown budget.
Its [source patch](data/subclass-mro-values-trial-20260930.patch),
[parent score](data/unpickle-subclass-mro-parent-rigorous-20260930.json),
[candidate score](data/unpickle-subclass-mro-candidate-rigorous-20260930.json),
[complete fixed gate](data/subclass-mro-fixed-baseline-gate-20260930.json), and
[complete parent gate](data/subclass-mro-immediate-parent-gate-20260930.json)
retain the evidence.

Two subsequent focused comparisons used the same default 21 balanced pairs
and five warmups for the suspect workloads. They are diagnostic checks of two
cases, not complete release gates. Ratios are candidate time divided by parent
time, so values below 1.0 are faster:

| Variant | `local_slots` ratio | `function_calls` ratio |
|---|---:|---:|
| Pointer-only membership | 0.961× (0.957–0.968×) | 1.023× (1.008–1.028×) |
| Pointer-only, outlined helper | 0.970× (0.958–0.977×) | 0.981× (0.978–0.988×) |

The pointer-only variant removed the local-slot slowdown but left a small
function-call cost. The outlined version removed that cost in this comparison
and retained the official unpickle gain in a fresh rigorous pair. Full fixture
runs passed with exit 0 for all three variants. Sources:
[pointer patch](data/subclass-mro-pointer-trial-20260930.patch),
[outlined patch](data/subclass-mro-outlined-trial-20260930.patch).
Focused data:
[pointer comparison](data/subclass-mro-pointer-targeted-parent-20260930.json),
[outlined comparison](data/subclass-mro-outline-targeted-parent-20260930.json).
