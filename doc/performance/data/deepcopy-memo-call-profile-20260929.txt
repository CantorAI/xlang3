Deepcopy memo call-path diagnostic (2026-09-29)

Purpose: locate the current pyperformance deepcopy_memo gap before changing the
VM. This diagnostic uses the pyperformance 1.14 benchmark's exact object graph:

    A = [1] * 100
    data = {"a": (A, A, A), "b": [A] * 100}

Timing method: 9 in-process samples, 25 copy.deepcopy(data) calls per sample;
report the median per-copy elapsed time from time.perf_counter. This is a
diagnostic, not a replacement for pyperf. Each runtime used the same script.

Existing VM profiling also showed the direct integer-key dict.get path is
eligible for memo lookups. The repeated calls to the pure-Python deepcopy
function and their frame/opcode execution are the next optimization target;
do not replace copy.py with a C++ implementation.

The fixed-baseline gate now includes this exact graph with 25 copy calls.
The full eight-case Release check against the preserved callmethodex baseline
passed: deepcopy_memo candidate/baseline ratio 0.992x. This is a regression
check only, not an improvement over CPython.

The standard pyperformance -p invocation could not create its XLang3 benchmark
venv here: ensurepip/get-pip bootstrap fails because the XLang3 executable
cannot initialize CPython 3.14's site.py. A direct runtime run with a fresh
PYTHONPYCACHEPREFIX succeeds, and the earlier full-run pyperf data is retained
in pyperformance-xlang3-vs-cpython314-20260928.md and its linked raw JSON.

Follow-up optimization (2026-09-29): XlangVMFrame::clear_for_pop now skips
resetting instruction-cache records whose adaptive domain is still Empty.
Every operation that can populate global, attribute, or call-site cache data
touches its domain first. This preserves cleanup and object-lifetime behavior
for used records while avoiding full record/vector resets for ordinary IR
instructions. The cache-domain invariant is documented at the cleanup site in
src/executor/xlang_vm/xlang_frame.h.
