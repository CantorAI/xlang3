Purpose: isolate the public Python wrapper cost from the existing native _json encoder.
Method: Release xlang3 and CPython 3.14.7 each ran scratch/performance/json-dumps-path-split.py; 4,000 calls per operation after one warm-up. This is a diagnostic loop, not a pyperf score.

Operation                              XLang3       CPython 3.14.7
EMPTY json.dumps                     13.970 us          0.833 us
EMPTY JSONEncoder.encode             10.997 us          0.672 us
EMPTY native encoder callable         0.649 us          0.106 us
EMPTY native callable plus join       0.953 us          0.123 us
SIMPLE json.dumps                    14.035 us          1.429 us
SIMPLE JSONEncoder.encode            11.414 us          1.312 us
SIMPLE native encoder callable        1.006 us          0.597 us
SIMPLE native callable plus join      1.299 us          0.610 us

Interpretation: XLang3's _json callable is close to CPython's native encoder for
these small values. The public Python wrapper path adds roughly 10-13 us per
call in XLang3, compared with under 1 us in CPython. The current target's
remaining gap is therefore mostly in executing the pure-Python json.dumps /
JSONEncoder.encode / iterencode layers, rather than in missing native JSON
code or registration. This identifies the next investigation area; it does not
by itself identify one exact VM opcode as the sole cause.

One XLang3 --perf-counters run of this diagnostic script observed these most
frequent VM operations across the whole script (including setup, all measured
paths, and output):
  LoadLocalAttr 193848
  LoadLocal     123487
  Call          114563
  LoadModuleSlot 105848
  StoreLocal     98763

Because the counters include benchmark harness work, they are exploratory and
should not be treated as per-json.dumps counts. The exact script is retained at
scratch/performance/json-dumps-path-split.py in the working tree used to collect
this follow-up.
