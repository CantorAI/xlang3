# Date serialization boundary: current XLang3 versus CPython 3.14.7

XLang3 is slower even when both interpreters run the same `_pydatetime` Python methods. In six balanced repetitions, the median date reduction loop took 2.516355 microseconds per operation on XLang3 versus 0.207360 on CPython's Python fallback. Four-byte state restoration took 8.043475 versus 0.379875 microseconds. These are approximately 12.1 and 21.2 times longer, respectively.

| Selection | Reduction (microseconds/operation) | Four-byte restoration (microseconds/operation) |
|---|---:|---:|
| CPython 3.14.7, public native `datetime.date` | 0.071155 | 0.040545 |
| CPython 3.14.7, explicit `_pydatetime.date` | 0.207360 | 0.379875 |
| XLang3, public Python fallback `datetime.date` | 2.516355 | 8.043475 |

All 18 children passed. Each child performs 10,000 direct bound reductions and 10,000 state constructors. All six permutations of the three selections are used. Setup, imports, metadata, checks and hashing are outside the timers; loop dispatch, result allocation/destruction and replacement remain included. The measurements are artificial component diagnostics, not official pyperformance scores, isolated kernel costs or proof of a whole-suite speedup. Short native loops are particularly sensitive to timing noise; all samples are retained.

The unchanged public `datetime.py` imports `_datetime`, falling back to `_pydatetime` on ImportError. CPython's public type comes from its native module; XLang3's public type is the Python fallback. CPython's tagged [native implementation](https://github.com/python/cpython/blob/v3.14.7/Modules/_datetimemodule.c) copies the stored four-byte date state when reducing and restoring it. The Python fallback executes field accesses, calls and byte-state construction. A native boundary difference and a slower execution path for the same Python body are both present. The latter contrast does not isolate function-call overhead from the other operations in that body.

The untouched official pickle workload contains one date in `DICT`, none in `TUPLE`, and none in `DICT_GROUP`: `mutate_dict` replaces values under string keys. There are 20 dumps per object and three objects per outer iteration, while pyperf declares 20 inner loops. These observed input and AST call-site counts establish workload structure, not executed reducer counts or a date time share. No component-time subtraction, additive fraction or projected official speed gain is reported. A date kernel alone must not be presented as the explanation for the whole pickle slowdown.

The earlier native `_pickle` safe-global/opcode work is already retained. Its discarded per-load date-class cache is a different mechanism and is not being repeated. An own native `_datetime` candidate is permitted because CPython implements that module natively; CPython DLLs/extensions and C++ translations of pure Python library algorithms remain excluded. A future candidate must preserve public class identity, subclass/override behavior, state/error semantics, ownership and GC traversal, and must pass the fixed gate plus the unchanged affected official benchmark. No engine change was applied for this diagnostic.
